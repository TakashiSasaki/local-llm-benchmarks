# Gemma 4 ページ分割・読み直しハーネス：追加試験

2026-11-18、前回の少数の実試験に続いて、BFCL Web-search由来の12問、重点確認3件、独自の動作確認3件を別runで実行した。後者の重点確認には同一問題の明示的な再試行2件を含む。BFCL公式ハーネスではなく、この結果は公式スコアではない。初回runも旧結果も保持した。

## 方式と改良

`integrations/page_harness/` は検索結果のURLだけをCrawl4AIに渡し、受け取った全文をローカルに保存して、見出し・部分読み・ページ内検索と位置指定による再読をモデルに提供する。ページに書かれた指示は未信頼データとして扱う。完全一致しないページ内検索には、語句が近い候補と元ページ内の位置を示すフォールバックを追加した。語句による順位付けであり意味検索でも正しさの証明でもない。見出し一覧はページ送りできる。

古い部分読みとページ内検索の結果は、設定した文字数閾値を超えるとページIDと位置等の参照に置換される。元本文、ハーネスの各リクエストと応答は保存する。部分読みの最新1件以上は保持し、今回の最後に加えた修正では、同じモデル応答からの複数の未提示の本文取得結果は次のモデル要求まで圧縮しない。複数同時取得の保護はオフラインの模擬試験で確認済みで、この18件では複数同時ツール呼出し自体は発生しなかった。

文字数による圧縮だけではトークン数を保証できないので、実際のチャットテンプレートとトークナイザーを使って、各要求の入力、32トークンの余裕、出力枠の合計が65,536を超えないよう調整する。圧縮できない部分が大きく残り枠がない場合は未完了で停止する。旧版138応答で入力推定が実測値より1少なかったため、この環境の先頭トークン1を追加した。調整後の15応答では入力推定が実測と一致した。他のランタイムやテンプレートへの一般化は未検証。

出典台帳にはツールが返したURL・ページID・位置・見出しを記録する。URL監査は、回答中のURLが本文を読んだページ、開いたが本文を読んでいないページ、検索結果だけで得たURL等のどれかを区別する。台帳とURL監査は、文脈や引用部分が主張を本当に裏付けるか、節番号が正しいかまでは判定しない。後処理の台帳は保存イベントから再構成したツール返却範囲であり、未完了時は最後の結果をモデルが実際に見たとは限らない。

## 12問の選抜試験

BFCL固定版 `f7cf735` の Web-search の質問から、事前の結果も参考に手で選んだ12問。モデルには検索スニペットを見せず、SearXNG MCPとCrawl4AI MCPを実際に使用した。サーバーからの検索結果は元ログに保存される。回答文字列は固定版の `agentic_checker` で確認した。これは大文字小文字等を整えたうえで正解候補の文字列が含まれるか調べる方法であり、回答の根拠や妥当性を精査するものではない。

| 区分 | 件数 |
|---|---:|
| 対象・実行 | 12 |
| 回答完了 | 11 |
| 完了回答のうち正解文字列に一致 | 8 |
| 完了回答のうち不一致 | 3 |
| 未完了・採点対象外 | 1 |

不一致の3件はいずれも必要な情報を確認できないとして回答を保留した。未完了は `web_search_4` で、旧上限20ターンおよび4ページの制約に達した。0点補完はしていない。成功したツール処理は検索36・ページ取得22・部分読み16・ページ内検索11。制限超過や外部サイトのブロック、検索元の失敗などによるツールエラーが計11件あった。旧版の件数カウンターは制限超過で拒否した呼び出しも含む。

圧縮は6問で計16回発生した。ただし、同じオフセットの本文が圧縮された後、その断片をモデルが自発的に読み直した事例はこの12問にはなかった。URL監査は完了11問のうち8問に警告を付けたが、数値のみを求める質問でURLを出さなかったケースなどを含むため、警告数を根拠誤りの数とはみなせない。後処理の台帳にはツールが返した範囲を残している。

同じ完了11問に対応する以前の保存済みBFCL実行では3問が正解扱いだった。ただし今回とはMTPの有無、生成設定、出力枠、指示、ツールAPI、ページ取得元、実行日時などが異なる。選抜も無作為ではないため、この差からハーネス単独の改善効果、一般的な正答率、または公式BFCLスコアを推定してはならない。

## 重点確認・限界

- `web_search_4` を別runで再試行し、ページ・ターン枠を増やしたところ最後まで回答した。しかし最大の湖として「最大の**自然湖**」Bantam Lakeを選び、保存正解のCandlewood Lakeとは一致しなかった。モデルが最終根拠としたBantam LakeのURLは検索結果から得たもので、その本文は読んでいない。新版のURL監査はこの状態を警告するが、自然湖と全ての湖の意味の違いまでは自動判定しない。
- `web_search_30` の別試行は正解候補のBelgiumを含んだが、回答に出典のURLを明示しなかった。本文取得元は台帳に残る。
- Python `json` と `urllib.parse` の2試験では、明示的に同じ位置の再読を指示し、0→2,400→0の順で取得した。最初の断片を圧縮した後に、保存ページから同一の文字列を再取得できた。これは指示付きの機能試験であり、自発的な再読の成功例ではない。
- 日本語のPython `json` 質問とRFC 9110のHEAD質問も試した。どちらも最終回答とURLを得たが、URLがあることは各主張に対応する抜粋をモデルが正しく読んだ保証ではない。

## 条件と記録の注意

Gemma 4 E4B IT Q4_K_M、llama.cpp b11960、全GPU配置、公式assistantを使うMTP ON、Thinking ON、コンテキスト65,536、モデル応答ごとの出力上限8,192、temperature 0.6、seed 42。実験中のMCPはSearXNG `2026.10.30+ffa88e3ba.local.4244dcfa4e4b`、Crawl4AI `0.9.5+local.4901cb2a4782`。強制的な圧縮試験のため、12問の閾値は6,000文字、後続試験は1,000文字とした。いずれも実運用の推奨値を示すものではない。

3 runのサンプルで観測されたシステム全体のGPUメモリ使用量のピークはいずれも6,757 MiB。これは推論プロセスだけを分離した値ではない。各runの実験用モデルサーバーは終了済みで、メモリ監視による強制停止はなかった。

12問runでは検索5、ページ4、read/find各15、20ターンが上限。後続2 runでは検索6、ページ6、read/find各18、30ターン。後続2 runの元manifestには古い `budgets_per_case` が残っており、同じmanifest内の新しい上限記述と矛盾する。実際の値は実行時のソースsnapshotと保存settingsにより確認し、`page-harness-analysis-20261118/effective-limits.json` に別途記録した。元manifestは変更していない。生成と失敗した外部呼び出しの自動再試行は行わなかった。元のrunに追加した派生集計や新しい記録は既存ファイルを上書きしていない。

MCP側が取得先へのリダイレクトをどう検証するかは、このクライアントから独立には検証していない。検索結果の情報だけではなく本文の該当部分に基づいて回答したか、質問の条件を満たしているか、必要に応じて人が確認する必要がある。
