# Local page-reading harness

An experimental local harness between llama.cpp and the user's SearXNG and Crawl4AI MCP endpoints. The model can search, open a search-result URL, search within saved text, and reread a bounded character range. Crawl4AI's `md` and `read_document` APIs are used to assemble the complete server snapshot into a local UTF-8 JSON file; IDs, offsets, source URL and SHA-256 remain in that file. A too-large or inconsistent snapshot is rejected instead of silently truncated. Page text is untrusted; the model is instructed not to follow instructions in it.

Old `read_page` and successful `find_in_page` excerpts are replaced by a page ID/offset or query reminder when tool text exceeds the configured character threshold; at least the newest excerpt is kept. New excerpts, including multiple results from the same assistant turn, are protected until the next model request has seen them. Original requests, responses and tool results remain in the run files. This trigger is a character-count heuristic: it is not a guarantee that all input fits. Before every model request the runner renders the actual chat template, counts its tokens plus one empirically observed BOS token for the tested llama.cpp build, reserves 32 slots, limits that request's output to the remaining context, and records/stops as incomplete if there is no room. The BOS adjustment needs revalidation for other runtimes or templates. Search snippets, other tool messages and model reasoning are not compacted by this version.

Literal in-page search falls back to ranked lexical candidates when there is no exact match; candidates are explicitly marked as approximate, and include offsets and the closest preceding heading. It is not semantic search and can miss or rank the wrong passage. `page_outline` paginates long heading lists. Each final result has a source ledger with the actual URLs and page ranges exposed to the model, separate from the model's answer, even when the requested answer format only permits a number. The ledger is a trace, not proof that a source supports a claim. The runner reports remaining per-tool budgets and turns to the model, and refuses to repeat an identical failed search/page request within a case; it does not retry inference automatically.

The runner starts/stops only its own Gemma MTP server. It uses the existing local command file `.local/humaneval-plus-20261117/gemma-mtp-fullctx-command-20261118.json` and the existing BFCL virtual environment. It sends model-generated search queries to the configured SearXNG MCP and selected URLs to Crawl4AI; those services may make external requests. It accepts only URLs returned by search and checks locally resolved addresses are public before requesting a crawl. Redirect handling is performed by the remote Crawl4AI service, not independently verified by this client. Authentication, access and rate-limit errors stop the run; failed cases are not retried automatically. The default live experiment uses two public questions, and each case has explicit search, page and turn budgets. The 12-case study stored its earlier 20-turn/four-page limits and earlier source snapshot; the updated defaults are 30 turns and six page opens.

For a new authorized trial, use a new run ID and pass one or more public questions. The command below does not preserve an automatic source snapshot; create one if reproducible benchmark evidence is required.

```powershell
& .local/bfcl-official-venv/Scripts/python.exe -B scripts/new_run.py --period period-004 --id period-004-page-harness-example --name "Page harness trial" --benchmark web-page-harness --type harness-integration --harness local-page-harness
& .local/bfcl-official-venv/Scripts/python.exe -B -X utf8 integrations/page_harness/run_probe.py --run period-004-page-harness-example --question "Your public research question here"
```

Use `--no-snippets` to withhold search snippets from the model; the complete SearXNG reply remains in the private run log. `--compact-chars 6000 --compact-keep 1` makes compaction more aggressive for testing and is not necessarily a production recommendation. Run offline tests with `& .local/bfcl-official-venv/Scripts/python.exe -B -m unittest discover -s tests -p test_page_harness.py -v`. Final-answer URL checking and the ledger do not verify that a quote, claim, or section number is correct. The caller must inspect evidence. This is a pilot harness, not an official BFCL adapter.

For saved runs, `audit_saved.py --run RUN_ID` creates a separate URL-exposure audit and `reconstruct_ledger.py --run RUN_ID` creates a separate ledger of read/find results; neither changes the original answers or events. A reconstructed ledger records tool-produced ranges and, especially in an unfinished case, does not by itself prove every range was presented to the model. Both refuse to replace an existing output. `evaluate_saved.py --run RUN_ID` applies the pinned BFCL answer-string checker to supported study inputs, but a substring match does not verify evidence or turn the pilot into an official BFCL score.
